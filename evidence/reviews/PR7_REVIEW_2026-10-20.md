## Findings

### P1 — Granted RBAC views fail for every tested role

`security/01_roles_and_grants.sql:8-16` grants view SELECT, while the three views use `SQL SECURITY INVOKER` and reference underlying tables for which these roles have no privileges. Customer, teller, manager, and auditor logins all received native error **1356** when reading their granted view. Auditor direct Audit_Log SELECT succeeded; direct Accounts SELECT and private-helper EXECUTE were correctly denied for all four roles.

Required B fix: implement a controlled view privilege model and verify it as actual restricted logins. Do not repair this by granting unrestricted base-table SELECT and defeating row isolation.

### P1 — Public banking APIs are unavailable to application roles

The RBAC script grants no EXECUTE rights on Member A public procedures. Customer and teller calls to `sp_deposit` failed with **1370**. Private-helper denial is correct and must remain. The RBAC script also hardcodes `bank_txn`, uses fixed role names, and is not installed by the integrated build; its manual installation requirement is documented but whole-system security acceptance is therefore not automatic.

Required B fix: implement the agreed public-procedure grant list with appropriate role policy, retaining private-procedure denial. Required A/B integration fix: provide safe target-aware installation and validation.

### P1 — View identity resolution disagrees with the banking resolver

`views/v_transaction_activity.sql` accepts both exact USER() and bare-user mappings together. With exact login mapped to customer 1 and bare login mapped to customer 2, A's resolver selected customer 1, but this view also returned one transaction for customer 2's account. A case-variant map was rejected by the resolver as System but matched the customer summary view, returning one row.

These were privileged diagnostic queries to expose filter behavior, **not a demonstrated low-privilege data leak**: restricted role queries currently fail with 1356. Fix identity precedence/case/ambiguity before enabling functional privileged views. Static review also found the activity view filters only Customer actors; intended employee visibility needs an explicit policy and tests.

### P1 — Required fraud interface remains incomplete

Actual routine inventory still lacks the seven SPEC functions: `fn_distance_km`, `fn_amount_zscore`, `fn_txn_count_window`, `fn_is_odd_hour`, `fn_account_age_days`, `fn_txn_risk_score`, and `fn_risk_level`. The newly implemented `fn_fraud_score` is not an approved equivalent public interface. Benchmark_Results, EXP-11..15 implementations, and the promised generators remain absent from the reviewed repository scope.

Required B action: implement the agreed components or obtain an explicit scope/interface revision. Required A action: retain legitimate contract checks rather than suppressing them to obtain a green report.

### P1 — Integrated build installs optimized indexes unconditionally

`build/run_all.sql:22` includes `indexes/01_performance_indexes.sql` without a baseline/optimized choice. Runtime inventory showed seven added indexes, five on the nine core tables. This conflicts with B0 (PK/UNIQUE/FK-required only) and invalidates a purported baseline installed through this path. Generating a new baseline snapshot after installing them would conceal the mismatch.

Required B/A integration fix: explicit baseline and optimized profiles with independent B0 checks. The benchmark file contains three EXPLAIN queries, not measured performance results; its suggested pre-index phase cannot be reproduced with the current integrated build. No benchmark was run in this review.

### P1 — Regression is not green in either mode

- `tests/functions/03_fraud_score.sql:4-5` expects 40 for `(100,'Online',FALSE,0)`; the implemented formula returns **30** (10 digital +20 untrusted). The other two score assertions pass. Resolve the agreed scoring expectation; do not silently adjust production semantics to a mistaken test.
- Existing source-order check: **133 PASS / 1 FAIL**, specifically `run_all.sql SOURCE data/seed/01_reference_data.sql`. CLI puts fraud rules/trigger before reference seed; Workbench order differs. Eight added B entries are labeled A in the ordered list.
- Standalone runner discovers B tests unconditionally: missing fraud function gives **1305**, and B object checks give four FAIL lines. Tests must select components by mode without weakening integrated assertions.
- B test files print unconditional PASS summaries even after failed assertions; the runner still detects preceding FAIL lines, but the summaries are misleading. The security smoke test only verifies four objects exist, not authorization or isolation.

### P2 — Re-evaluation changes fraud outcomes without new activity

`sp_evaluate_fraud.sql:28-30,46-63` feeds the stored account score back into the next score and updates that stored score again. Repeating evaluation of the same clean opening transaction produced **60.00 -> 100.00 -> 100.00**, without another ledger transaction. Unique flag keys prevent duplicate rows, but scores and rule matches drift. Define reproducible reevaluation semantics and test them; the source description says the routine is safe to call repeatedly.

### P2 — Rule configuration is ignored; credit-leg policy needs agreement

The evaluator branches on fixed rule codes/thresholds and never reads `param_json`. Setting HIGH_AMOUNT minimum_amount to 1,000,000 still flagged a 6,000 deposit. If configurable rules are intended, implement their semantics; otherwise document the fixed rule contract and remove misleading configuration expectations.

A trusted-device transfer's credit leg correctly has NULL device under A5, yet receives UNTRUSTED_DEVICE. This is an observed false-positive/policy compatibility concern, not a claim that the present missing-device rule violates an explicit exemption. Agree whether transfer credits should inherit context, skip that rule, or intentionally flag missing context without changing A5.

### P1 acceptance blocker / A integration tooling

`tests/run_regression.ps1` targets `bank_txn`/`bank_txn_scratch`; rebuild/test wrappers restrict database names to those databases. Procedure PowerShell tests 15 and 18 also rebuild fixed scratch targets. Consequently the original complete PowerShell regression could not be safely executed under this review's protected-database rule. The regression script also retains unconditional blocked security reporting despite newly available B objects.

`experiments/run_all_auto.ps1` still has no `-Quick` parameter (confirmed by command metadata); it exposes Database/SkipThroughput/ResumeThroughput instead. The requested Quick path remains blocked. It was not invoked, and no full experiment workload was substituted.

Required A fix: isolated-target support throughout nested runners, mode-aware tests, accurate capability detection, synchronized source ordering, selectable index profile, and a real bounded Quick interface. These are follow-up requests only; no source was changed during review.
