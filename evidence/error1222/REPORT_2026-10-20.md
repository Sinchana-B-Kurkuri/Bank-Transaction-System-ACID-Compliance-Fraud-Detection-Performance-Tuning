## Exact root cause and correction

`procedures/sp_evaluate_fraud.sql:34-35` selected six expressions into five variables:

```sql
SELECT t.account_id,t.amount,t.channel,t.device_id,a.customer_id,t.transaction_timestamp
INTO v_account,v_amount,v_channel,v_device,v_txn_ts
```

The corrective patch removed v_customer but retained a.customer_id, then added transaction_timestamp. There is no customer variable or other consumer for that projection anywhere in the evaluator. The account join and all predicates remain needed/preserved as existing behavior; only the extra projection was removed:

```sql
SELECT t.account_id,t.amount,t.channel,t.device_id,t.transaction_timestamp
INTO v_account,v_amount,v_channel,v_device,v_txn_ts
```

This aligns five values with five destinations and preserves the intended timestamp mapping. It is a SELECT...INTO arity error, not a UNION mismatch. The reference-data UNION ALL arms have equal widths; reconciliation UNION arms also align. The actual runtime call chain is:

`p3_load_tiny_seed -> sp_open_account -> sp_internal_post_single -> sp_internal_insert_ledger -> Transactions INSERT -> trg_transactions_ai_fraud_evaluate -> sp_evaluate_fraud`.

MySQL reports the outer CALL line, so the failing batch line need not identify the SELECT inside the evaluator. The exact original routine from Git was installed, and its real loader CALL reproduced the reported native error.
